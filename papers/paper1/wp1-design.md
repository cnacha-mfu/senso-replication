Scope: design only. No repo files were modified. The toy experiments ran with `/home/adtgrade/research/senso-framework/.venv/bin/python` (Owlready2 0.51, bundled Pellet 2.3.1 and HermiT) and Java at `~/research/tools/jdk/bin/java` (Temurin 25). Fuseki was not touched.

## 0. Summary

1. **Pellet works and is the right primary reasoner.** On this VM, with this JDK, Pellet:
   - evaluates SWRL built-ins over data values (`lessThan`, `greaterThan(OrEqual)`, `abs`, `multiply`, `matches`, `startsWith`, `endsWith`);
   - classifies individuals into defined classes built from datatype restrictions;
   - handles negation for else-branches, 2-of-3 voting and "X unless Y" overrides with no Python logic;
   - returns justifications through its `explain` CLI. Owlready2 has no explanation API, but the CLI can be called on the bundled jars.

   HermiT gives the same labels on every SWRL-free encoding I tried. It rejects SWRL built-ins, which confirms the earlier finding on the real SEO ontology.
2. **Open-world negation is not a problem for measured data.** When a data property is `FunctionalProperty` and its value is asserted, `not (p some decimal[>0.3])` is entailed for a value of 0.04. Else-branches, majority votes and override precedence can all be written as OWL 2 DL class expressions. Pellet's justification even names the axiom `Functional locMKp` as the source of the closure. Missing measurements give *no* label ("undetermined"), not a false one.
3. **Required profile: OWL 2 DL plus DL-safe SWRL.** `pellet info` reports `OWL 2 DL`, with expressivity `ALCF(D)`, or `ALCOF(D)` once nominal closure axioms are added. EL, QL and RL are ruled out because `ObjectComplementOf` and `ObjectUnionOf` appear in equivalent-class axioms, and those are needed for else-branches and votes. SWRL is needed only to compare one measurement with another (for example "second-half mean ≥ 0.9 × first-half mean") and for string matching in AgentCommit.
4. **Five pitfalls that would break the implementation if unknown, all found by experiment:**
   - a. **Datatype mismatch.** Owlready writes Python `float` as `xsd:decimal`, while `populate.py` emits `xsd:double`. Declaring range `decimal` and then asserting a `double` literal makes the ontology **inconsistent**. Without the range axiom, a `double` literal silently fails to match a `decimal[>=0.3]` restriction. SWRL built-ins compare numerically across both types. Fix: use `xsd:decimal` for every real-valued measurement.
   - b. **Explanation renderer crash.** Pellet's explanation renderer throws a `ClassCastException` when a union contains an anonymous data restriction. Rule: every disjunct and every negated operand must be a named class. The fix was tested.
   - c. **`xsd:pattern` facets crash Pellet 2.3.1** (`UnsupportedOperationException`). Use SWRL `matches` instead.
   - d. **Pellet slows down superlinearly with many commit individuals.** 1k commits took 4.7 s, 3k took 33 s and 5k took 106 s. HermiT is linear: 5k took 2.6 s and 20k took 6.9 s. Commit-level classification has to be chunked.
   - e. **Namespace split.** The TBox uses `…/seo/seo-entities#` and similar, while the ABox from `populate.py` uses `…/seo#`. The CQs and `generate.py` use a third vocabulary. Today no ABox triple refers to a TBox class.
5. **Some old labels will change, and this cannot be avoided** (Section 7). The main causes are measurement bugs found during the inventory:
   - Law I is always "conformant", because zero-commit months are never created.
   - "Monthly LOC" is the summed NLOC of the files touched that month, not the size of the repository.
   - Insufficient data is currently written as a law **violation**.
   - The thresholds published in the paper's law table are not the ones that produced the real-repo labels.

### (b) Safe conformance without creating individuals: **works, two ways**

Pattern 1 pre-asserts one assessment individual per repo × law:

Pattern 2 classifies the repo directly into `Law4ConformantRepo`, as in (a).

**Recommendation:** classify the repo directly with `LawNConformantRepo` and `LawNNonConformantRepo` classes, disjoint pairs. This needs no extra individuals, is simpler to explain, and works without SWRL for single-measure laws.

The essential rule: **the non-conformant class is defined by the complementary threshold, written positively.** A SWRL-derived class cannot be negated usefully under the open-world assumption, because the absence of a rule firing proves nothing.

### (d) Non-monotonic needs (else-branches, votes, overrides): **works without Python judgement**

The full legacy ensemble (`test_scenarios.py:79-182`) as defined classes. Every operand is a named class, and every data property is Functional:

**Universal conditions with asserted closure** ("all months …", needed for Law V per-month and for monotone/recent-rising): **works.**
```python
class FamiliarityBreakMonth(MonthSnapshot): equivalent_to=[MonthSnapshot & locChangeRatio.some(D(min_exclusive=0.4))]
class FamiliarMonth(MonthSnapshot):         equivalent_to=[MonthSnapshot & locChangeRatio.some(D(max_inclusive=0.4))]
class LawVNonConformant(Repo): equivalent_to=[Repo & hasMonth.some(FamiliarityBreakMonth)]           # OWA-safe
class LawVConformant(Repo):    equivalent_to=[Repo & hasMonth.only(FamiliarMonth) & hasMonth.some(MonthSnapshot)]
r.is_a.append(hasMonth.only(OneOf(all_month_individuals)))     # ABox closure assertion
```
```
closure=False HermiT/Pellet {'rOK': ['Repo'],            'rBAD': ['LawVNonConformant']}
closure=True  HermiT/Pellet {'rOK': ['LawVConformant'],  'rBAD': ['LawVNonConformant']}
```

**What cannot be expressed in OWL or SWRL here: comparing two counts**, for example Law VIII's "corrective months ≥ 0.5 × rising months". Qualified cardinality needs a constant. SWRL cannot aggregate.

**Trade-off, stated plainly.** Python may assert the counts (`monthsWithComplexityRise`, `monthsWithCorrectiveActivity`), because counting is measurement. The comparison and its 0.5 coefficient then live in a SWRL rule (`multiply` + `greaterThanOrEqual`). Python must **not** pre-compute "votes", booleans that already contain a threshold, or differences that bake in coefficients (for example `cg − 0.5·lg`). Those would leak judgement into Python.

Threshold-free shape descriptors (for example `commitsMonotoneNonIncreasing`) are measurements in principle. The per-month closure encoding is still preferred, because it keeps window lengths such as "last 3 months" inside the ontology, and explanations then name the actual months.

## 3. Design

### 3.1 Measurement/inference boundary

**Python may:**
- count, sum and average;
- compute statistics with no decision cut-off (Mann-Kendall τ, S, p and Sen slope; CV; half-means; ratios of two measurements);
- extract raw strings (trailers, author name, branch name);
- assert per-month snapshots and closure axioms.

**Python may not:**
- compare against a constant;
- choose a branch based on a measurement;
- emit booleans that encode a threshold;
- write any `seo:*Stage`, `Law*`, anti-pattern or `AgentCommit` type.

Mechanical "done" test: put every label-deciding axiom in a sixth module, `seo-inference.owl`. Load the TBox without it, run Pellet, and assert that zero label triples appear. Then `grep` `populate.py` for numeric comparisons outside the measurement helpers.

### 3.2 Measured data properties

All are Functional. Reals are `xsd:decimal`, rounded to 6 dp and written as `Decimal(str(round(x,6)))`; counts are `xsd:integer`. NaN and inf are **not asserted** and give "undetermined". The domain is `seo:SoftwareProject` unless stated. Each property gets an `rdfs:comment` giving unit and computing function, plus `seo:computedBy "measures.py:fn"`.

| Property | Range / unit | Computed by (new `ontology/population/measures.py`) | Used by |
|---|---|---|---|
| `monthsObserved` | integer, months | `monthly_series()`, **zero-filled over the lookback window** (fixes Law I/CV bias) | all (minimum-history guards) |
| `activeMonthRatio` | decimal [0,1] | months with commits / monthsObserved | Law I (pipeline) |
| `meanMonthlyCommits`, `commitsLast3Months` | decimal / integer | series stats | Law I (scenario variant) |

### 3.3 Rule and axiom set (in `seo-inference.owl`)

All constants come from `ontology/modules/thresholds.yaml`. Each threshold entry has id, value, unit, rule, source, `status: JUSTIFIED|UNJUSTIFIED` and a sensitivity range. The builder bakes the values into the axioms and attaches an `seo:thresholdId` / `seo:thresholdSource` annotation to each class. WP4's sensitivity analysis then means: rebuild the TBox with varied thresholds and re-reason the **unchanged** ABox. No re-mining is needed.

Notation: `p[op k]` means `p some decimal[op k]`. `Has(p…)` means `p some decimal` for each listed p. Every operand of ⊔ and ¬ is a named class.

**Guards.** `SufficientHistory6 ≡ monthsObserved some integer[>=6]`; `MKApplicable ≡ locSeriesLength some integer[>=4]`.

**Laws, canonical "pipeline" variant** (keeps continuity with the real-repo labels; WP4 may switch to the "paper-table" variant, built from the same template):

| Law | Conformant | NonConformant |
|---|---|---|
| I | `Has(monthsObserved≥2) ⊓ activeMonthRatio[>=0.5]` | `… ⊓ activeMonthRatio[<0.5]` |
| II | SWRL: `complexityHalfMeanSecond ≥ complexityHalfMeanFirst` → `LawIIConformant` | SWRL `lessThan` → `LawIINonConformant` |
| III | `SufficientHistory6 ⊓ churnCV[<2.0]` | `SufficientHistory6 ⊓ churnCV[>=2.0]` |
| IV | `SufficientHistory6 ⊓ commitCountCV[<1.5]` | `… [>=1.5]` |
| V | `monthsObserved≥4 ⊓ linesAddedCV[<2.0]` | `… [>=2.0]` |
| VI | `GrowthStage ⊔ StabilizationStage` (chained inference over inferred phase) | `DeclineStage` |
| VII | SWRL `multiply(?t,?f,0.9), greaterThanOrEqual(?s,?t)` | SWRL `lessThan(?s,?t)` |
| VIII | `SufficientHistory6 ⊓ MergeActive ⊓ MultiAuthorActive`, where `MergeActive ≡ mergeMonthRatio[>0.3]` and `MultiAuthorActive ≡ multiAuthorMonthRatio[>0.3]` | `SufficientHistory6 ⊓ (MergeInactive ⊔ MultiAuthorInactive)` |

Plus `DisjointClasses(LawNConformant, LawNNonConformant)` for each law. These pairs are the consistency guarantees: an ABox that ends up in both classes is reported as inconsistent, with a `pellet explain --inconsistent` justification.

Paper-table variant (`test_scenarios.py:185-310`):
- III and V use per-month classes and the 3-branch LOC-growth split with named branch classes.
- II, VII and VI use endpoint measures. VII's `∨` becomes a union of named classes.
- VIII's count comparison uses SWRL `multiply(?k, ?rising, 0.5), greaterThanOrEqual(?corr, ?k)` over counts that a post-reasoning SPARQL aggregate takes from inferred MonthSnapshot classes (`RisingMonth ≡ complexityDelta[>0.1]`, `CorrectiveMonth ≡ correctiveCount[>5]`, `ResponsivePair` via `nextMonth some CorrectiveMonth3`).

**Phases.** Single classifier, per WP3. Two encodings are provided:
- *MK stage rules*, exact equivalent of `PhaseDetector`, since pymannkendall gives "increasing" ⇔ p<α ∧ S>0:
  - `GrowthStage ≡ MKApplicable ⊓ locMKpValue[<0.05] ⊓ locMKTau[>0]`
  - `DeclineStage ≡ MKApplicable ⊓ locMKpValue[<0.05] ⊓ locMKTau[<0]`
  - `StabilizationStage ≡ MKApplicable ⊓ Has(locMKpValue, locMKTau) ⊓ ¬GrowthStage ⊓ ¬DeclineStage`
- *Legacy ensemble*, the exact `test_scenarios.py:79-182` logic as in (d):
  - The f2-vs-k·f1 comparisons become SWRL pairs (`multiply` + `greaterThan` / `lessThanOrEqual`), each producing a named class, so else-branches can negate *OWL-defined* classes only. A SWRL-derived class has to be paired with its positive complement, not negated.
  - The monotone and recent-rising overrides use per-month closure classes:
    - `CommitIncreaseMonth ≡ commitDeltaFromPrev[>0]`, and `CommitsMonotone ≡ Repo ⊓ hasMonth only ¬CommitIncreaseMonth`. Use a named `NonIncreaseMonth ≡ commitDeltaFromPrev[<=0]` so explanations render.
    - `RecentRising ≡ hasMonth only (OlderThanLast2 ⊔ LocRoseMonth)`, with `OlderThanLast2 ≡ monthIndexFromEnd[>=2]`.
    - The 5% three-month LOC growth is a measured ratio, `locGrowthLast3`, with the threshold in the class.

  WP3 decides which encoding labels real repos. The other stays as a regression artefact.
- `AllDisjoint(GrowthStage, StabilizationStage, DeclineStage)`. These map onto the Rajlich & Bennett stage classes that WP3 will add, through `rdfs:subClassOf` or `owl:equivalentClass`.

**Anti-patterns** (`test_scenarios.py:350-366`; rename `ShadowTechDebt` per D4, e.g. `AgentAssociatedComplexityGrowth`):
- Single-measure thresholds become defined classes.
- Cross-measure comparisons (`cg > 0.5·lg`, `lg > 3·cg`, LOC/feature > 800) become SWRL rules with `multiply` / `divide`. **`divide` has not been tested yet; test it first.**
- Each anti-pattern is a class on `SoftwareProject` (for example `ExhibitsDependencySprawl`) rather than a pattern individual. This avoids minting individuals.

**AgentCommit** (R1.M3). `AgentCommit ≡ AgentCommitByTrailer ⊔ AgentCommitByBotAuthor ⊔ AgentCommitByBranch`, defined by SWRL string rules as in (f):
- Trailer regexes copied from `AGENT_COAUTHOR_PATTERNS`.
- Bot author: `endsWith "[bot]"`. The `codex`/`devin` substring rule should become an explicit WP1 decision.
- Branch rules from `agent_detector.BRANCH_PATTERNS`.
- **Message markers and "touches CLAUDE.md" are dropped.**
- `seo:agentType` becomes subclasses (`ClaudeCodeCommit`, …), one SWRL rule per vendor pattern.
- HermiT-compatible alternative for later: `hasCoAuthor some AgentIdentity`, with curated identity individuals.

**Bug-fix commits** (decision needed). Either keep keyword classification as a cited *measurement instrument* (MSR convention; WP4 must cite it), or move it into the ontology with `matches` on `commitSubject` → `BugFixCommit`, plus a SPARQL aggregate. The second is more consistent with the thesis but costs another commit-level pass.

### 3.4 Pipeline: reasoning on the live ABox and writing back to Fuseki

Per repository (an embarrassingly parallel unit; **at most 2 to 3 concurrent reasoning workers on this VM**: Pellet runs with `-Xmx2000M` by default, and Fuseki already holds 4 GB):

1. **Mine and measure** (Python, timed `t_mine`, `t_measure`). Build ABox triples with decimal/integer typing and the closure assertions.
2. **Write the asserted graph** `urn:senso:abox:{repo}` with a Graph Store Protocol `PUT /seo/data?graph=…`, which is atomic and idempotent (`t_load`).
3. **Read it back**: `CONSTRUCT … FROM <urn:senso:abox:{repo}>`. The reasoner then sees exactly what the store holds, which is the honest version of "reasoning on the populated ABox".
4. **Stage A, commit level.** Load the TBox from local `.owl` files (record its sha256) plus the commit individuals in chunks of 1,000. Run `sync_reasoner_pellet` in a `with inferred:` block. Collect `AgentCommit*` types.
5. **Aggregate** (SPARQL over asserted + stage-A inferred): `recentAgentCommitRatio`, agent adoption date = `MIN(authorDate)` of `AgentCommit`, and optional `BugFixCommit` ratios. Assert these as measurements in `urn:senso:abox-derived:{repo}`. This is a stratified pipeline (reason → aggregate → reason). Aggregation is counting, not judgement, and the paper should state the stratification explicitly.
6. **Stage B, repo level.** Load the TBox plus the repo, MonthSnapshot and derived ABox, then run Pellet (`t_reason`, also record ABox triples and individuals). Inconsistency is a reportable outcome. Capture it with `pellet explain --inconsistent` instead of failing the run.
7. **Write the inferred graph** `urn:senso:inferred:{repo}:{tboxhash}`. Write *all* label types (`INDIRECT_is_a` filtered to `seo-inference` classes), because Fuseki does no subclass inference. Add provenance on the graph: `prov:wasGeneratedBy` run, reasoner "Pellet 2.3.1 (Owlready2 0.51 bundle)", jar sha256, TBox sha256, timestamp, timings.
8. **Explanations** (`t_explain`). For each inferred label in a whitelist (stage, 16 law classes, anti-patterns, and *one sample per evidence class* for AgentCommit), call `pellet explain --instance ind,Class --max 1` with RDF/XML on stdin. Parse the Manchester output:
   - `Rule(...)` / `X equivalentTo …` lines become `seo:usesAxiom <classOrRuleIRI>`;
   - `ind prop value` lines become `seo:usesFact [seo:onProperty p; seo:value v; seo:subject ind]`;
   - `Functional p` lines become `seo:usesClosure p`.

   Store these as `seo:Justification` nodes in `urn:senso:explanations:{repo}:{tboxhash}`, and keep the raw text in `seo:explanationText`.
9. **Readers** (`generate.py`, CQs, the v2 runner) query the union of the graphs, using `FROM` clauses or `tdb2:unionDefaultGraph`. They **never** recompute labels.

**Explanations as manifest provenance.** Each label class carries an annotation `seo:explanationTemplate`, for example `"no significant LOC trend (Mann–Kendall τ = {locMKTau}, p = {locMKpValue}, {locSeriesLength} months)"`. The generator fills it **only from the facts in the justification**, which guarantees that every number in the manifest is one the reasoner used. Long universal (closure) justifications are summarized deterministically ("all 24 months ≤ 40% LOC change; max 12% in 2025-03"). Negative results ("why not growth?") are not entailments; they are explained by the positive complement class (for example `NoTrend`).

**Timing.** Write `results/real_v2/wp1_reasoning_times.json` with per-repo `t_mine`, `t_measure`, `t_load`, `t_reason_A` (by chunk), `t_aggregate`, `t_reason_B`, `t_explain` (n calls) and `t_writeback`, plus ABox triples/individuals and commit count. Also measure a **JVM baseline** (Pellet on an empty ABox, about 1.5 s here) and report reasoning time with and without it. Plot reasoning time against commit count; the Pellet curve is superlinear without chunking.

**Profile statement for the paper.** OWL 2 DL (`pellet info`: ALCF(D), or ALCOF(D) with nominal closure) plus DL-safe SWRL with built-ins, which Pellet supports. The SWRL-free subset also runs on HermiT and can be offered as a reasoner cross-check (identical labels were observed). Pellet 2.3.1 is old. Pin `owlready2==0.51`, record the jar hashes, and mention Openllet as the maintained fork.

## 5. Risks and open decisions

- **New measurements** (feature commits, refactorings, dependency history, PR branch names) add mining cost and GitHub API load. If they are dropped, the ensemble shrinks to LOC + commit signals, which WP3 may prefer anyway.
- **Bug-fix keyword instrument**: decide between "measurement instrument with citation" and "ontology rule".
- **Stratified pipeline**: aggregates over inferred commit labels go through SPARQL between two reasoning passes. Say so in the paper.
- **Explanation cost**: about 1.8 s per call. With roughly 25 labels per repo that is about 45 s per repo. Acceptable at 2–3 workers. A long-lived JVM, for example via JPype, is an optimization, not a requirement.

## 7. Where old labels will necessarily change

1. **Insufficient data**: the old code writes `conforms=False`, which is published as "VIOLATION" in manifests. The new design gives no label ("undetermined").
2. **Law I**: always conformant before (no zero-commit months existed). Zero-filling changes it, and also changes CVs III/IV/V and the Law VIII ratios.
3. **Phase on real repos**: changes once "LOC" becomes real repository LOC instead of the summed NLOC of touched files, and once the `nloc>0` month filter is removed. Law VI changes with it.
4. **Single classifier (WP3)**: whichever encoding is chosen, either the real-repo labels (if the ensemble is adopted) or the scenario accuracy (if MK is adopted) changes. The published κ = 0.68 / 95% cannot both carry over.
5. **Published thresholds ≠ the pipeline's** (CV 0.45 vs 1.5, and so on). Every law label changes if WP4 adopts the paper-table variant.
6. **AgentCommit**: commits found only by message markers ("auto-generated by" also matches things like protoc output) drop out. Branch evidence adds new ones. Adoption dates move. All agent commits are classified, not a sample of 200.
7. **Anti-patterns**: never computed on real repos before, so they are entirely new labels with no baseline.
8. **Exact-boundary values**: rounding to decimal(6) may flip them. The differential test will list them.
